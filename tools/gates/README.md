## The numbers of the gates

The number after the name of the script in the `justfile` (for example `130.110`) is the number of the task that wrote the gate. The numbers `130.xxx` are tasks of `feat-5-foundation-monorepo-ci`. A gate of a different feature has the number of the task of the feature. `just lint` and `just test-lint-gate` have `110.115` (the task of `feat-6-contracts-openapi-pipeline`). `just breaking-changes` and `just test-breaking-changes-gate` have `115.110` and `115.130`. `just generate`, `just compile`, `just test-generate-gate` and `just api-docs` have `120.120` and `120.130`. `just check-generated`, `just test-check-generated-gate` and `just test-build-gates` have `130.100` and `130.105`. A number can be the same as one of feat-5 (the `130.xxx`): the name of the script tells them apart. The number is only in the message `NOT IMPLEMENTED` of the recipe `_gate`. The message names the task that writes a script that is not in the folder.

## The base that the gates compare with

`just validate` and `just commit-check` compare with the branch that the pull request goes to. The value `base` at the top of the `justfile` gives it. If the value `GITHUB_BASE_REF` is set and not empty, `base` is `origin/` and the value of `GITHUB_BASE_REF`. If not, `base` is `origin/dev`. In GitHub Actions, `GITHUB_BASE_REF` is a value that the runner gives (the target branch of the pull request). The workflow has no `env:` (the gate `check-workflows` does not have `env:` as correct). `actions/checkout` with `fetch-depth: 0` gets all branches. `origin/dev` and `origin/main` are in the clone. `just breaking-changes` also uses `base`. It does not compare with the last commit of the branch. It uses `git merge-base <base> HEAD` and the OpenAPI file at that commit (DEC 93594b2b-be54-4f60-9f53-ec2ce6c84be4, rule 1). The merge base has the history as necessary. The CI job has `fetch-depth: 0` as necessary (a clone with no history has no merge base, and the gate stops). On your machine, `GITHUB_BASE_REF=main just commit-check` compares with `origin/main`. Examine the value with `just --evaluate base`.

Release case: for a pull request from `dev` to `main`, the range `origin/main..HEAD` has each commit of `dev` that is not in `main`. The range also has commits that are not new. The gate does not ignore a commit that is not correct. Merge a release with a merge commit (not a squash merge and not a rebase merge). The next release range has only the new commits. See `branch-protection.md` in the folder of feat-5 and the plan.

Each script gives exit code 0 if the gate goes on. It gives a different code if the gate stops. The scripts that read a workflow or an SBOM give 2 if a file is not correct and the gate finds a problem in its input.

## The gate for generated code

`just check-generated` (`check-generated.sh`, test: `test-check-generated-gate.sh`, ACC-004 and ACC-009 of feat-6). The folders are `<backend dir>/src/generated` and `<frontend dir>/src/generated`. The folders are committed.

**The gate compares with HEAD.** In CI the work tree is HEAD (the copy of the merge commit of the pull request). "The code in the repository" is the work tree. The gate compares the new generation with HEAD. The gate does not let `generate.sh` cover a change by hand. `generate.sh` deletes the two folders and makes them again. A change that is only in the work tree is not there before the check. Such a change is not committed, not in the index of git, or ignored by git. The gate examines the folders before it makes the code. The gate stops if git shows a line for the folders:

1. a file with the value `assume-unchanged` or `skip-worktree` of `git ls-files -v` (git status does not show a change of such a file);
2. a line of `git status --porcelain --untracked-files=all --ignored -- <folders>`. The line is a file that is changed or deleted (in the work tree or in the index of git). It is a file that git has no record of (`??`). It is a file that `.gitignore` ignores (`!!`, for example `Extra.class` or `x.log`). `git status` looks at the index and at the work tree. It lists the files in a new folder one by one (`--untracked-files=all`). `git diff` knows only the files that git has a record of. The gate sets `core.fileMode=true`. A change of the mode counts.

Then it examines the marks (ACC-009), makes the code, and starts the same `git status` again. After step 2 the work tree was HEAD. Each line is a difference between HEAD and the new generation:

| Line | Meaning | Case of ACC-004 |
|---|---|---|
| ` M <file>` | The generated file is not the file of HEAD | a change by hand, or a change of the OpenAPI file with no new generation. The marker `.openapi-generator/*.sha256` has the hash of the OpenAPI file that the plug-in read. A new `info.version` shows in the marker |
| ` D <file>` | HEAD has a file that the generators do not make | a file in the folder that the generators do not make |
| `?? <file>` | The generators make a file that HEAD has not | a deleted generated file |
| `!! <file>` | The same, and `.gitignore` ignores it | |

A change of a comment of `contracts/openapi.yaml` gives the same files. The gate does not stop for the change. A change of `contracts/openapi.yaml` that is not committed is no problem for the gate (it uses the file of the work tree). The committed generated code must be the code for it.

**On a developer machine.** The gate stops for a change in the generated folders that is not committed. The flow is: change `contracts/openapi.yaml`, `just generate`, `git add`, `git commit`, `just check-generated`. The message names the lines it found. The message has the text that the gate compares with HEAD. The gate stops before the generation, if git shows a line for the folders, on the machine and in CI. The gate never overwrites a change that exists only in the work tree. A change that is in the index of git is a change that is not committed too (the status line is `M `, `A ` or `D `).

**The marks.** The gate examines the committed code. The `README.md` of each folder has the title `Generated code, do not change`. Each Java file has `@Generated(`. Each TypeScript file has the text of Kubb at its start. Each folder has one or more Java or TypeScript files. A mark that is missing stops the gate before the generation, with the cause.

**The gate does not examine:** the API documentation (`build/api-docs`, not committed), and the dependencies of the Maven plug-ins (GitHub issue #23). The gate finds a changed output of the plug-in. The gate does not name the dependency that changed. The generated code has no value from the machine (REQ-011). `test-generate-gate.sh` examines the time zone, the locale and the working folder.

## Rules of the review of feat-5

These rules come from the review of feat-5 after the work (the points E1, E2, G1 and G2). Each rule has tests with bad input in `selftest.sh`.

### E1: a manifest that no gate scans (`sbom.sh`)

Before the change, `sbom.sh` scanned only `pom.xml`, `backend/pom.xml`, `frontend/package.json` and `frontend/pnpm-lock.yaml`. A manifest in a position that is not scanned gave an empty SBOM. The license gate wrote `PASS` with 0 components. After the change:

## Maven Wrapper

The wrapper is in `backend/` (`feat-6-contracts-openapi-pipeline`). It has no jar (`distributionType=only-script`, and `*.jar` is in `.gitignore`). It has no `mvnw.cmd` (the project has no Windows build; the recipes have `bash` as necessary). To change the Maven version:

1. Change `MAVEN_VERSION` and `MAVEN_SHA512` in `tools/versions.env` (the sha512 of the `.tar.gz`, from the `.sha512` file of the release).
2. Make the files again with the wrapper plug-in: in an empty folder, start `mvn org.apache.maven.plugins:maven-wrapper-plugin:3.3.4:wrapper -Dtype=only-script -Dmaven=<MAVEN_VERSION>`, and copy `mvnw` and `.mvn/wrapper/maven-wrapper.properties` to `backend/`. The plug-in writes no `distributionSha256Sum`. Add the line by hand.
3. Get `apache-maven-<version>-bin.zip` and its `.sha512` file from Maven Central and from `archive.apache.org`. The two `.sha512` files must be the same. `sha512sum` of the download must give that value. Then `sha256sum` of the download is the `distributionSha256Sum`. Do not copy the value from a different position (not from the properties file from before and not from this `README.md`).
4. `backend/mvnw` has the git mode 100755 (`git update-index --chmod=+x backend/mvnw`).
5. Start `just check-pins`, `just sbom` and `just license-check`.

- `fixtures/`: input for the self-test of `check-sudo.sh`. The files have the extension `.fixture`. No gate reads them as a script.

A code owner reviews a change in this folder (see `.github/CODEOWNERS`). The scripts do not use `sudo` (REQ-008).

## Limits

- The check for `sudo` is a check of the text. It does not see a word that a script builds from parts.
- The commit check does not accept the messages that git makes (`Revert "..."`, `fixup! ...`). Write `revert(feat-N): ...`. The commits with the first line `fixup! ...` become one commit (squash).
- `sbom.sh` is not examined in `just test-gates` with the Maven and pnpm manifests of the project. The test uses stubs. The first start with the `backend/pom.xml` and the `backend/mvnw` of the project is done (`feat-6-contracts-openapi-pipeline`, Task 105.110, 2026-11-04): `just check-pins`, `just sbom` and `just license-check` give exit code 0 on this repository. The `pom.xml` has no dependency. The SBOM has 0 components. This start did not examine a license of a library. The plug-in of the project writes an SBOM with no `components` key for a project with no dependency. `license_check.py` stops for such a file. After the change `sbom_check.py` writes `"components": []` to the file in the SBOM folder in this case. The case is a `pom.xml` with no dependency only. The case has tests with stubs. The part of `feat-6-contracts-openapi-pipeline` that made the generators added the dependencies of the generated code and the `frontend/` of the project. It started the gate again. `just sbom` and `just license-check` give exit code 0. The SBOM has 12 components of the Maven module (Apache-2.0). It has 102 components of `frontend/` (93 MIT, 3 Apache-2.0, 3 ISC, 2 BSD-3-Clause and 1 PSF-2.0). The SBOM has no `jakarta.annotation-api`. The agent started `sbom.sh` one time by hand with a `pnpm` workspace of the project (see the plan of feat-5). The part of feat-6 that examined the licenses started it on a scratch module with libraries and a scratch `frontend/` (see the plan of feat-6).
- **The dependencies of the Maven plug-ins are not examined** (GitHub issue #23, it stays open for a full pinning). This feature pins only the jar of each plug-in that it adds: `cyclonedx-maven-plugin` (`CYCLONEDX_MAVEN_PLUGIN_SHA256`) and `openapi-generator-maven-plugin` (`OPENAPI_GENERATOR_MAVEN_PLUGIN_SHA256`). The dependencies of these two plug-ins are not examined by a hash of this project. For example: the jar of the generator that has the generators `spring` and `html2` and their templates. The plug-ins that Maven 3.10.0 gives for the build (`clean`, `resources`, `compiler`, `surefire`, `jar`) are not examined too. The Maven Wrapper examines only the sha256 of the Maven download. The jar of the generator plug-in has a hash. The code that makes the files is in the jar of the generator and in the dependencies of the plug-in. A changed dependency can change the generated code without a failure of the pin. The gate for generated code (`just check-generated`) finds a change of the output.
- The first start did not examine these items. It did not examine the dependencies of `cyclonedx-maven-plugin` and of the other Maven plug-ins (GitHub issue #23). It did not examine the Maven download (`mvnw` examines only its sha256; the contents of `apache-maven-3.10.0-bin.zip` are not in the SBOM). It did not examine the other plug-ins that Maven 3.10.0 starts for `clean`, `compile`, `test` and `package` (the SBOM gate starts only the plug-in `cyclonedx-maven-plugin`).
- The gates do not examine the inputs of a `uses:` step. The check has only the versions of the actions that install the tools (for example `with:` of `actions/checkout`). The gates do not examine the value of `runs-on`. They do not examine the `<modules>` of a `pom.xml`.
- The CI job `test-gates` has the network as necessary. Maven Central is for the Maven Wrapper and the plug-ins. The npm registry is for the installs of Spectral and cdxgen. GitHub is for the download of oasdiff. A time without service of a registry can make the required check `test-gates` stop without a change in the project. The job has no cache action: `actions/cache` is not in `tools/license/allowed-actions.txt`. A new action is a decision of the owner (REQ-014 of `feat-6-contracts-openapi-pipeline`). The risk is smaller if the owner adds `actions/cache` (MIT) to the table and to the job. The job has a cache for `~/.m2`, the pnpm store and `build/tools/`. The job has 30 minutes until it stops.
- The CI jobs `check-generated`, `compile` and `api-docs` start the Maven plug-ins (`openapi-generator-maven-plugin` and the plug-ins that Maven 3.10.0 gives) with dependencies that have no pin (GitHub issue #23) and with network access (Maven Central). `contents: read` and `persist-credentials: false` of the step `actions/checkout` keep the risk small. The job has no right to write. The job has no values for access in the work tree. The gate for generated code finds a change of the output of the plug-ins.
- The Python tools are examined with all their dependencies (see G2 above). The checksum of `uv` is not in this project (`UV_VERSION`; the action `astral-sh/setup-uv` gets it). The GitHub Actions are pinned by a commit SHA only. The Python build that `uv` gets is a managed Python 3.13 (when the machine or the runner has none). No hash of this project examines the two. The dependencies of the Maven plug-ins are not examined (GitHub issue #23). The dependencies of cdxgen are examined by its lock file, with one case that is different. A different integrity value of an optional dependency does not stop the install. pnpm does not install that package. The lock file does not examine pnpm (the tool that installs): pnpm is pinned by `PNPM_VERSION` (the install script and `pnpm/action-setup`).
